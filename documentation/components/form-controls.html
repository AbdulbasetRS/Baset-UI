Form Controls

The layout and text around form fields: groups, labels, help and error messages, fieldsets, and vertical or responsive horizontal layouts. CSS only.

01. Installation & Include

Form Controls is part of the Core stylesheet, so assets/css/baset-ui.css is the only file required. It is CSS only: the layout classes style plain div, label, fieldset and legend elements. The icon Extension is needed only if an Input Group example uses an icon.

<link rel="stylesheet" href="assets/css/baset-ui.css">
<!-- Optional: icons inside an Input Group. -->
<link rel="stylesheet" href="assets/css/extensions/baset-ui-icons.css">

<div class="bui-form-group">
    <label class="bui-form-label" for="email">Email</label>
    <input class="bui-input" id="email" type="email" aria-describedby="email-help">
    <div class="bui-form-text" id="email-help">We will not share it.</div>
</div>

03. Default

We will not share it.

A group is a grid: the label, the control and the help text are its children, one per row. The text is linked to the control with aria-describedby, and the label with for and id.

Note

The breakpoints are viewport media queries, not container queries: a horizontal group inside a narrow column on a wide screen is still horizontal. A fieldset cannot be a horizontal group, because the browser does not place a legend as a grid item. For a horizontal group of radios or checkboxes use a div with role="radiogroup" (or role="group") and aria-labelledby that points to a bui-form-label, as in the Examples section.

Fieldset and legend

Notifications

Use a fieldset and legend for a set of related controls (a radio group, a set of checkboxes): the legend is announced with each control.

Validation

States are plain: is-valid and is-invalid on the control, aria-invalid="true" for invalid (the invalid style applies to either), and an error message linked with aria-describedby. The library does not run validation: use the browser's Constraint Validation API (checkValidity(), validationMessage, setCustomValidity()) and toggle the classes, as in the form below. The script is page code, not a library API.

At least 3 characters.
Used only to reply.
form.addEventListener('submit', function (e) {
    e.preventDefault();
    Array.prototype.forEach.call(form.elements, function (el) {
        if (!el.willValidate) { return; }
        var ok = el.checkValidity();
        el.classList.toggle('is-valid', ok);
        el.classList.toggle('is-invalid', !ok);
        if (ok) { el.removeAttribute('aria-invalid'); } else { el.setAttribute('aria-invalid', 'true'); }
        var msg = document.getElementById(el.getAttribute('aria-describedby'));
        if (msg) {
            msg.classList.toggle('bui-form-text--error', !ok);
            if (!ok) { msg.textContent = el.validationMessage; }
        }
    });
});

When a field becomes valid again the message keeps the last error text; reset it to your help text if you want it back. The browser's validationMessage is in the browser language, not the page language: write your own messages (and translate them) when that matters.

Floating label

Not provided, on purpose. A floating label depends on a placeholder that is present but invisible, shrinks the label text while the field is focused, and changes position when the direction changes. A visible label above the control keeps the label readable at every size and is the safer default. This is a documented decision of Task 12, not an omission.

06. JavaScript API

CSS only, no JavaScript API. Form Controls registers nothing with BUI.register, fires no events and has no options to parse. It has no internal text, so it adds no key to assets/i18n/*.json: the labels, help text and messages are what you write (use data-bui-i18n with your own keys to translate them). The validation script in section 04 is page code that uses the browser's own Constraint Validation API.

07. Responsive Behavior

  • Base (below 480px): groups are one column and as wide as the form. Inputs fill the width of their group.
  • bui-form-group--horizontal-sm, -md and -lg turn from one column into two at 576px, 768px and 992px; --horizontal is two columns at every width, so it needs a container wide enough for a 9rem label column (use a breakpoint variant on narrow screens).
  • The label column is a token (--bui-form-horizontal-label-width); the control column takes the rest and can shrink to nothing without overflowing, so long values and wide controls never push the page sideways.
  • On touch devices (pointer: coarse) inputs grow to at least 40px, 44px and 48px (small, medium, large) and check controls rows to 44px.
  • The breakpoints are viewport media queries: the Playground preview width does not trigger them (see the note in the Playground documentation).

08. Accessibility

Keyboard

Form Controls adds no behavior: Tab order is the source order, and every native control keeps its own keys. Tab order was verified on a sample form (text, email, tel, checkbox, switch, button).

ARIA and semantics

  • Every control has a visible label linked with for and id (or wraps the control). A placeholder is not a label.
  • Link help and error text to the control with aria-describedby (several ids are allowed, separated by spaces).
  • Mark a required field with the required attribute. The asterisk from bui-form-label--required has an empty text alternative, so it does not become part of the accessible name. Browsers that do not support the alternative-text syntax in content show the same asterisk and may read it aloud.
  • When a field is invalid set aria-invalid="true" and show the message as text. The invalid style also adds a thicker edge, so the state is not only a color.
  • Group related controls with fieldset and legend, or with role="group" or role="radiogroup" and aria-labelledby.

Contrast

Measured in Chromium on the manual test page for every state (Light and Dark, the default and ocean themes, LTR and RTL): 1,024 samples for the Form Controls, Input, Checkbox, Radio and Switch pages together. Text (label, help, error and success text, input text, placeholder, addon text) is at least 5.07:1 (AA needs 4.5:1). Non-text parts (input border, check border, checked fill, tick, switch thumb, focus ring) are at least 3.73:1 (AA needs 3:1). Disabled controls are exempt from contrast and were not counted.

Screen reader

Not tested with a screen reader (NVDA, VoiceOver or similar). Not tested in Safari or Firefox, with a real touch device, or with real browser autofill (the autofill rule exists and was only checked for syntax; the headless test browser cannot trigger autofill).
