Input

A styled native text input and textarea, with sizes, read-only, disabled and validation states, prefixes and suffixes, and an optional password toggle.

01. Installation & Include

Input and Textarea are part of the Core stylesheet, so assets/css/baset-ui.css is required. They are CSS only, except the optional password toggle, which also needs assets/js/baset-ui.js (and the icon Extension for the two eye icons). Load baset-ui.js before your own scripts; it starts the toggle on its own (BUI.init runs when the page is ready).

<link rel="stylesheet" href="assets/css/baset-ui.css">
<!-- Only for icons inside an Input Group and for the password toggle. -->
<link rel="stylesheet" href="assets/css/extensions/baset-ui-icons.css">

<label class="bui-form-label" for="name">Name</label>
<input class="bui-input" id="name" autocomplete="name">

<!-- Only for the password toggle (and translated labels). -->
<script src="assets/js/baset-ui.js"></script>

02. Customize

Every option below is a real class or attribute documented in section 04. Options that do not apply to a combination are ignored in the code (for example, the password toggle needs the password type and a button).

03. Default

bui-input styles the native input and textarea: nothing about how they work changes (typing, required, pattern, the Constraint Validation API, autofill). It is full width and medium by default.

04. Variants & Options

Types

The class works on the text-like types: text, email, password, number, search, url, tel and date (the native date control, drawn by the browser: its picker and format are not customized), and on textarea. Select, file, color, range, checkbox and radio inputs are not styled by bui-input (see the Checkbox, Radio and Switch pages for the last two).

Textarea

Text direction

Text aligns to the start side (text-align: start) and follows the page direction. Two attributes help in RTL pages:

  • dir="ltr" on fields that always hold left-to-right values: email, URL, telephone, number, codes. The value and the cursor stay left to right even in an RTL page.
  • dir="auto" on free text that may be written in either direction: the field takes the direction of what is typed. Measured in Chromium in an RTL page: typed Arabic is right to left, typed Latin text is left to right. An empty field with dir="auto" resolves to left to right, so its placeholder sits at the left edge until text is typed. If the placeholder should sit at the right in RTL, leave dir off.

Input Group

An bui-input-group puts a prefix or suffix next to the input: text or an icon in bui-input-group__text, or a button. The children share their borders and only the outer corners are round (logical corners, so it mirrors in RTL). A focused or invalid child is raised so its border is never hidden. Group sizes (bui-input-group--sm, --lg) size the input and the text; size the buttons with bui-btn--sm and --lg (the heights match).

Text addons are decoration for sighted users: link a meaningful one to the input with aria-describedby (first example) or put the meaning in the label. An icon-only button needs an accessible name (aria-label).

Password toggle

The optional toggle shows or hides the password. Put the button in the group with data-bui-password-toggle, aria-pressed="false" and aria-controls set to the input id. It has one accessible name ("Show password", translated by data-bui-i18n-attr) and its state is exposed with aria-pressed, so the name does not change. The two icons are swapped by CSS from the state. The input type is reset to password when the component is destroyed.

06. JavaScript API

Input and Textarea are CSS only. The only JavaScript is the optional password toggle, registered as password-toggle in baset-ui.js and started by BUI.init() from data-bui-password-toggle. It has no options. The instance is BUI.getInstance(button, 'password-toggle') (or the factory BUI.passwordToggle(button)).

Attributes

aria-labelyesThe accessible name. Use data-bui-i18n-attr="aria-label:form.showPassword" to translate it (key added to en, ar and fr).

07. Responsive Behavior

  • Inputs are full width of their container at every width and never cause horizontal scrolling; inside an Input Group the input shrinks (min-inline-size: 0) and the addons keep their size.
  • Long text in an Input Group addon does not wrap (white-space: nowrap), so keep addons short on narrow screens.
  • On touch devices (pointer: coarse) the minimum heights grow to 40px, 44px and 48px (small, medium, large); the group text and buttons follow so a row stays level. Verified with a coarse-pointer emulation in Chromium.
  • Browsers zoom the page when an input smaller than 16px is focused on some phones; the default size uses 1rem text, the small size 0.875rem. This was not tested on a real phone.

08. Accessibility

Keyboard

Native: Tab and Shift+Tab move between fields, typing, selection and the date picker behave as the browser defines. The password toggle is a button: Enter or Space toggles it, and it is a normal tab stop after the input. The focus ring is the global ring drawn around the field.

ARIA and semantics

  • Every input needs a visible label (or an aria-label when a design hides it). A placeholder is not a label.
  • Invalid fields get aria-invalid="true" and an error message linked with aria-describedby.
  • The password toggle keeps a constant name and reports its state with aria-pressed; its icons are aria-hidden.
  • A read-only field is focusable and read normally; a disabled one is skipped by Tab.
  • Use the right type and autocomplete values so assistive technology and browsers can help (email keyboard, autofill).

Contrast

Measured in Chromium on the manual test page for every type and state, in Light and Dark, the default and ocean themes and LTR and RTL (1,024 samples with the other Task 12 pages): input text and placeholder at least 5.07:1 (AA: 4.5:1); input, valid and invalid borders and the focus ring at least 3.73:1 against the page (AA for UI components: 3:1). Disabled fields are exempt and not counted.

Forced colors

Borders stay visible (the system draws them) and valid and invalid use the highlight color. Checked only with the forced-colors emulation of Chromium, not on Windows.

Screen reader

Not tested with a screen reader (NVDA, VoiceOver or similar). Not tested in Safari or Firefox, on a real touch device, or with real browser autofill.
